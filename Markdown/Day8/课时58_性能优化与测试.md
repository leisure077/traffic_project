## 二、本项目用到的优化手段（呼应 Day12 讲义）

1. **向量化替代循环**：时间转换、距离、速度、布尔过滤全部整列运算；
   反例：`apply`/逐行循环最慢，能用列运算就别用 apply。
2. **广播一次性算距离矩阵**：避免 Python 双层 for。
3. **分批处理大数据**：热力 25.6 万点按 1 万一批匹配，控制内存。
4. **距离矩阵只算一次复用**：选 K 时各 k 共用同一个 `D`（O(n²) 只付一次）。
5. **按用户分组聚类**：单人点数量小，避免在全量点上做巨大 O(n²)。
6. **教学抽样**：SAMPLE_ROWS=20000，把流程压到约 24 秒；全量也能跑，只是更慢。
7. 其他常见手段（了解）：category 类型压缩字符串内存、`read_csv` 指定 dtype/usecols 减少读取、`multiprocessing` 多进程按用户并行、`lru_cache` 缓存重复计算、chunk 分块读超大文件。

### 一个小实验：apply vs 向量化

```python
s = pd.Series(range(1_000_000)) / 10
%timeit s.apply(lambda x: x*2)      # 慢
%timeit s*2                         # 快很多
```

## 三、测试：让代码"改不坏"

### 1. 为什么测试重要

阈值、列序、时间戳逻辑稍改就可能出错。给核心函数写测试，改代码后一键回归，心里有底。

### 2. unittest 示例（可放 test_utils.py）

```python
import unittest
from utils import haversine, parse_time

class TestHaversine(unittest.TestCase):
    def test_same_point_zero(self):
        self.assertEqual(haversine(123.4, 41.8, 123.4, 41.8), 0.0)

    def test_known_distance(self):
        d = haversine(123.4119, 41.8052, 123.4370, 41.8033)
        self.assertAlmostEqual(d, 2.1, delta=0.3)   # 太原街->中街约2km

    def test_unit_m_km(self):
        self.assertAlmostEqual(haversine(123.4,41.8,123.41,41.8,unit="m"),
                               haversine(123.4,41.8,123.41,41.8)*1000)

class TestTime(unittest.TestCase):
    def test_parse(self):
        self.assertEqual(parse_time("20181003123000").year, 2018)

if __name__ == "__main__":
    unittest.main()
```

运行：`python -m unittest test_utils.py`。

### 3. pytest（如已安装）

同样的 `test_` 函数用 `assert` 即可，还能 `pytest --cov` 看覆盖率。

### 4. 建议优先测试的纯函数

- `haversine`（同点为 0、单位换算、已知距离）；
- `kmeans`（明显两团能分开、空簇不产生 NaN）；
- `decide_purpose`（夜间长停留→居住；商场 POI→购物；景点 POI→旅游；窗口覆盖修复后旅游可达）；
- 毫秒时间戳 +8 转换（首行应为 2018-10-03）。

## 四、调试与日志

- `logging` 比 print 更适合长期项目（可分级、可写文件）；项目用轻量 `log()` 已带时间戳和级别。
- `pdb`/IDE 断点：在循环里看 labels、shape；常见先看 `df.shape`、`df.head()`、`df.dtypes`。
- 防御性处理：文件不存在抛清晰错误、merge 前对键去重、除零/异常速度过滤。

# 课时 45：出行目的（下1）——时间规则与"窗口覆盖"陷阱

## 一、纯时间规则（讲义原始口径）

按停留时长与起止时刻推断：

- **居住**：duration > 4h 且（start 或 end 在夜间 0-6 / 20-23）；
- **购物**：start ≥ 9 且 end ≤ 21；
- **旅游**：start ≥ 9 且 end ≤ 17；
- **其他**：都不满足。

讲义给的判定**优先级**是：居住 > 购物 > 旅游 > 其他。

## 二、陷阱：购物窗口把旅游完全覆盖（真实逻辑 bug）

注意两个时间窗：

```
购物：9:00 ───────────────────── 21:00
旅游：9:00 ──────── 17:00
```

旅游窗 `[9,17]` 是购物窗 `[9,21]` 的**子集**。如果先判购物：

```python
if 居住条件: return "居住"
if start >= 9 and end <= 21: return "购物"   # 所有9-17的段在这里就被拦截
if start >= 9 and end <= 17: return "旅游"   # 永远执行不到！
```

**旅游永远返回不了**。实跑验证：严格按这个优先级，结果是 居住234 / 购物221 / 旅游0 / 其他285——旅游恒为 0，这显然不合理（数据里明明有 80 个旅游 POI）。

> 这是一类经典错误：**多个 if 条件存在包含关系时，宽条件放前面会让窄条件永远不可达**。判断分支能否被覆盖（覆盖率思维）是重要的工程素养。

## 三、纯时间也无法真正区分购物与旅游

即使调换顺序，9-17 点内的一次停留既可能是逛商场也可能是游景点，**时间本身区分不了**。真正携带"购物 vs 旅游"信息的是空间：附近是商场还是景点。这正是提供 POI 静态数据的意义。

## 四、本项目的修正方案（时间定居住，POI 定购物/旅游，时间兜底）

`purpose.py` 的 `decide_purpose`：

```python
def decide_purpose(row):
    s, e, dur = row["start_hour"], row["end_hour"], row["duration_hours"]
    # 1) 居住：长时间且端点在夜间
    if dur > LIVING_DURATION_THRESHOLD and (is_night(s) or is_night(e)):
        return "居住"
    # 2) 空间证据：1000m内最近POI是购物/旅游，直接采用
    poi_type = row.get("nearest_poi_type")
    if bool(row.get("match_success", False)) and poi_type in ("购物", "旅游"):
        return poi_type
    # 3) 时间兜底：先窄后宽
    if s >= 9 and e <= 17:
        return "旅游"
    if s >= 9 and e <= 21:
        return "购物"
    return "其他"
```

设计要点：

1. 居住仍由"时长+夜间"强时间特征决定；
2. 白天活动优先采信最近 POI 类型（把旅游 POI 用起来，修复旅游=0）；
3. 没有匹配 POI 时再用时间兜底，且**先判更窄的 9-17，再判 9-21**，避免覆盖；
4. 阈值全部来自 config（居住 4h、购物 9-21、旅游 9-17）。

修正后实跑：**居住 234 / 购物 165 / 旅游 112 / 其他 229**，四类齐全且合理。

## 五、工程顺序：先匹配 POI，再判目的

因为判定要用 `nearest_poi_type`、`match_success`，代码里把"POI 最近邻匹配"放在"综合判定"之前（下一课实现），这也修正了讲义"空间匹配只做验证、不影响结论"导致的旅游不可达问题。

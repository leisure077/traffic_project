# 出行实训 · 交通时空数据分析（traffic_project）

从沈阳运营商**基站信令定位数据**里识别每个人的**出行 / 驻留**行为，再判断**出行目的**、
**出行方式**，并输出**商圈实时热力**，最后画出 6 张结果图（另附 2 张讲清中间过程的附加图）。

一条命令跑完 8 个模块：

```bash
python main.py
```

---

数据目录（`原始数据.csv` 等 6 个输入文件）**不放在项目内**：`config.py` 的
`_find_data_dir()` 按下面的顺序找，第一个含 `原始数据.csv` 的目录即命中：

1. 环境变量 `TRAFFIC_DATA_DIR`；
2. `traffic_project/data/`（讲义的兜底：把 6 个 CSV 直接放包内，包就能脱离仓库跑）；
3. 仓库根的 `data/raw/`（本仓库实际命中这里）；
4. 仓库根的 `交通时空数据分析数据/`、`相关数据/`，以及 `../data/`；
5. 都没有再从仓库根往下扫两层。

全都没命中时 `main.py` 会**直接停住**并打印上面三条出路，而不是带着缺失的输入去跑
八个模块刷八屏 traceback——「没数据」和「某个模块算错」是两类问题，后者才走容错继续。

## 四、算法链

```
原始信令 532,828 行（10 列无表头）
   │  ① 清洗：去脏 imsi → 去空编号 → 毫秒UTC+8时区 → 目标日 → 关联基站补经纬度
   │         → 排序 → 分钟去重 → 每人≥20点 → 整用户抽样（放在全部规则之后，见下文）
   ▼
cleaned_data.csv                        imsi,time,lac_id,cell_id,lon,lat
   │  ② 阶段1：标记低频点（同用户同坐标<4次，不删）→ 切连续段 → 相邻点速度>8km/h
   │           命中的到达点**连同它的出发地那一点**一起算疑似出行
   ▼
stage1_travel_points.csv                + speed（高召回粗筛，宁可多留）
   │  ③ 阶段2：经纬度先投影成米（否则欧氏距离把地图横向压扁 25%）→ 逐用户手写 K-Means，
   │           K=2~10 用「轮廓系数 + 0.1×邓恩指数」选优；基线是「不拆分记 0 分」，
   │           所以同一个基站那种坐标完全相同的点不会被硬拆成两簇
   ▼
stage2_cluster.csv                      + cluster, is_single_cluster
   │  ④ 阶段3：簇心到首/中/尾三点 <1000m 且 首末跨度 <2h → 驻留，否则出行；
   │           单点簇直接判出行；未参与聚类的点默认驻留（label 1=出行 0=驻留）
   ▼
stage3_label.csv                        全量点 label
   ├─ ⑤ label==0 切驻留段 → POI 空间证据 + 时间窗兜底  → purpose_result.csv
   ├─ ⑥ label==1 切出行段 → 站点邻近点数证据 + 速度兜底 → mode_result.csv
   └─ ⑦ 实时流（自带经纬度）→ 最近商圈匹配 → 命中点分两条路：
         ├─ 滚动之前按 (商圈, 小时) 计数                  → heat_hourly.csv   （图5 用它）
         └─ 分钟×商圈计数 → 补齐 1440 分钟 → rolling(10) 求和 → heatmap_result.csv
   ⑧ 六张必交图 + 两张附加图（簇划分、总览拼图）                     → result/figures/
```

三条设计线贯穿全程：

- **漏斗式**：阶段1 求召回、阶段2 看结构、阶段3 求准确，每一步都在纠正上一步的偏差；
- **证据优先**：目的与方式都先找空间证据（POI / 站点），证据不足才用时间窗或速度兜底，
  且**窄条件必须排在宽条件前面**（旅游窗 `[9,17]` 是购物窗 `[9,21]` 的子集，
  写反了旅游会恒为 0）；
- **口径统一**：类别顺序、配色在 `config.PURPOSE_ORDER / MODE_ORDER` 里固定，
  报告表格和柱状图用同一份顺序，不会出现图文对不上。

**抽样排在 9 条规则全部跑完之后**（课时 28 的整用户抽样不是清洗规则）：
原先它排在规则6 前面，抽的是"还没补经纬度、还没分钟去重"的行，20,000 行过完后面几条
只剩 17,362 行，产出率 87%，少掉的 2,638 行等于白抽。挪到末尾后同样抽 20,000 行目标，
实得 **19,983 行 / 239 个用户**（原来 17,362 行 / 196 个）。代价是全量清洗多花约 0.9 秒
（2.6s → 3.5s，全流程 10.5 秒），换到的是每条下游统计都多两成样本、
且地铁这类要靠"沿线多个站点"证据的类别从 5 段涨到 20 段（低频点改为标记不删后进一步到 242 段，见第七节）。

## 六、自检

`python tools/selfcheck.py` 打印 6 项 PASS/FAIL：

1. 手写 K-Means 能把三团人造数据分对（准确率 > 99%）；
2. 向量化 Haversine 与逐点循环数值一致（相对差 <1e-6，实测差 2.33e-10），且至少快 5 倍
   （各跑 3 轮取最快再算比值——这两段是 11ms/125ms 量级，单次计时受 Windows 时钟粒度、
   调度和冷启动影响很大：同一份代码在仓库目录实测 10.7~11.3×，在刚拷出来的新目录实测
   8.2~12.9×。阈值原先卡在 10× 正好落在噪声带里，会一次 PASS 一次 FAIL，自检结论就不可复现）；
3. 阶段3 不变量：标签仅取 0/1、覆盖清洗全量点、整簇同标、
   出行点数 = 单点簇点数 + 多点簇判出行点数（精确相等），并抽 60 个多点簇用纯 Python
   重算三点判据比对标签；
4. 阶段2 可复现性：同种子两次 `choose_best_k` 标签与最优 K 逐位相同；
5. 目的/方式口径：旅游 > 0（死代码回归防护）、四类齐全、站点证据门槛不被绕过；
6. 交付产物：7 个 CSV + 6 张 PNG 齐套。

## 七、与老师示例图的差异

示例图一共 6 张，我们的图**画法有三处照搬了示例，判定口径有三处故意不照搬**。逐条说明。

### 照搬的部分（只动画图，不动任何数据）

| 图 | 示例的做法 | 我们原来的做法 | 现在 |
|---|---|---|---|
| 图2 24 小时曲线 | 出行、驻留两条线画在同一个坐标系里 | 拆成上下两格各画一条 | 同轴叠画。两处口径改完后出行与驻留量级接近（驻留约为出行的 2 倍），共轴直接看得清，中途为"红线被压成平线"补的放大格已删掉 |
| 图5 商圈热力 | 全表共用一条绝对人次色标；数字只写深色格；矩阵贴到色标条、右侧不留白 | 一度按每行自己的最大值上色（中街峰值 215 会画得和太原街 2570 一样红）；后来又在行尾加了一列「峰值 X」、把 xlim 撑出 3 格空白 | 全部改回示例的做法：绝对色标 + 只给 ≥ 最大值一半的格子写数字 + 无峰值列。数字口径见下面单独一节 |

### 我们主动改过的两处判定口径

**① 低频点只标记不删除。** 课时 32 的口径是"同用户同坐标出现不到 4 次的点删掉"，
但速度 >8km/h 的点里有 **83.7%** 恰好落在这些"只出现过一两次"的基站上——
人移动路上只会路过同一个基站一次，删掉等于把出行样本删没（3.1%）。
现在统计照做、打上 `is_low`、一行不删。出行率 3.1% → 25.6%。

**② 一次移动的出发地和到达点都算出行。** 信令点本身不含运动信息，一次移动是由
「前一个位置 + 后一个位置」这一对点共同证明的；只标终点，等于宣布出发地那条记录是驻留，
可人当时已经离开这个基站了。多出的 1,764 个"只作出发地"的点全部交给阶段2/3 复核，
误标的会被判回驻留。出行率 25.6% → **33.6%**（6,723 / 19,987）。
补齐纪要要求的两条清洗规则（规则2 imsi 必须 15~20 位纯数字、规则6 剔沈阳经纬度区间外的漂移坐标）
之后，样本变 19,983 点 / 239 用户，出行率 **34.4%**（6,880 / 19,983）——下面引用的 33.6% 一律是
改清洗前的读数，两档差 0.8 个百分点，不影响任何结论。

### 不照搬的部分（照搬会把已经修掉的问题带回来）

**图1 出行占比：示例 42.3%，我们 34.4%。** 为了确认剩下的差距不是"我方数据处理把底层数据
弄坏了"，把组员的三段判据原样搬到我们这份 19,987 点上跑了一遍（脚本 `_exp/their_rules.py`，只读实验）：

| | 组员的判据 | 我们的判据 |
|---|---|---|
| 我们的整用户样本 19,987 点 | 40.3% | 3.1% |
| 组员的随机抽行样本 691 点 | 39.8% | 3.3% |

（右列是**上面两处口径改之前**实跑出来的，两份数据用的都是当时的判据。）

换数据只动 0.5 个百分点，换判据动十几个点——**底层数据没有失真，差距全部来自口径**。
改完①②之后我们到 34.4%，与组员那 40.3% 之间剩下的 5.9 个点，就是下面两条我们不采纳的规则：

- 组员的出行点 91% 来自"进了簇又被阶段3 翻成出行"，其中 **71% 只因为"离自己簇的中心超过 1 公里"**。
  这条依赖 K 选得多小：K 偏小则簇偏大，正常在家过夜的点也会离簇心超 1 公里，被判成移动。
  我们用"簇心到首/中/尾三点 <1000m"，量的是簇本身的尺度，不受这个影响。
- **11.7% 只因为"到下一个点超过 2 小时"**。一个人回家睡整觉，半夜本来就没有信令，
  醒来后的下一个点天然隔 7 小时——按这条会被判成"整晚在路上"。

先前写在这里的"一天 42% 在移动不合常识"这句论证已经删掉：我们自己的数据在 23 时的出行占比
就到了 40% 以上，晚上十点以后还在动的点大量存在，那条推理站不住。
现在的分歧点只落在上面两条具体规则上，答辩按这两条讲。

**图3 出行目的：示例旅游 0 笔、其他 84.7%、居住 0.8%。** 旅游时段（9-17 时）正好被购物时段
（9-21 时）整个包住，如果先查购物，所有本该是旅游的段会先被购物吃掉，旅游永远轮不到——
0 笔是漏判而不是沈阳没人旅游。我们的顺序是**先查范围窄的、再查范围宽的**，
两处口径改完后驻留段切出 1,396 段，分出 购物 458 / 其他 368 / 旅游 351 / 居住 219。
示例那份"其他"占 84.7%、"居住"只有 0.8%，是上游把一天切得太碎：段太短就没法判断，
而一个人一天里在家过夜，本该有驻留段落到"居住"。

**图4 出行方式：形状接近，样本量仍差一档。** 示例 1,360 段，我们 1,136 段
（地铁 307 / 公交 323 / 其他 275 / 小汽车 231）。原因是抽样方式：按行随机抽会把一个用户的一天
切成半截，半截段既判不了目的也判不了方式；我们按整用户抽，并把抽样挪到 9 条规则全部跑完之后。

### 图5 单独说明：三方数的不是同一个量

图5 是六张图里唯一"数字对不上、而且差得最多"的一张，所以单独交代。先把结论摆前面：
**三方（我们 / 老师示例 / 组员）用的是同一份实时流数据，中间结果逐小时一致，
差别全部出在最后画图那一步一个格子里塞了几个人。**

证据：`实时流数据.csv` 三方 md5 完全相同；我们的 `heatmap_result.csv` 与组员那份
按同一写法相加后 **23/24 小时比值 = 1.000**，全天合计只差 0.13%。清洗、1000m 最近商圈匹配、
10 分钟滚动窗口三段全部对得上，所以既不是算法问题也不是清洗问题。

差别在这个格子取什么值：

| 口径 | 太原街全天 | 相对真实人次 | 23 时那一格 |
|---|---|---|---|
| **每小时命中人次**（我们现在这张） | 130,245 | **1×** | 12,502 |
| 老师示例（按像素反读标定，误差中位 0.3%） | 375,656 | **约 2.9×** | 32,187 |
| 组员的图：把同小时 60 个互相重叠的窗口全加起来 | 1,295,827 | **10×** | 127,214 |
| 我们旧图5：一小时内只取最挤的那一个窗口 | — | 约 0.2× | 2,570 |

两条推论：

- **老师那张不可能是人头。** 它光太原街一行就 375,656，而整份实时流一共 256,212 行——
  一行超过全表，说明它自己也是重复计数的产物（最贴合的实现是 30 分钟窗口每 10 分钟取一个点）。
  组员的图比老师的还大 4 倍。**"我们和示例不一样"从来不是我们单方面偏了。**
- **我们选 1× 这一档，理由是它是唯一能讲清楚的那个量**：一小时内出现过多少人就是多少人。
  形状上它和示例也贴得上——逐时曲线各自归一化后相关系数 **0.946**（5 时谷底、17 时后拉起、23 时最高）。

实现上有个坑必须写在这：小时人次**只能在滚动窗口之前统计**。`heatmap_result.csv` 存的是
1440 个分钟里每个过去 10 分钟的累计，一小时内那 60 个窗口互相重叠，按小时求和等于把同一个人
数 10 次。所以 `heatmap.hourly_counts()` 紧跟在 `match_business()` 之后、`rolling()` 之前落一张
`heat_hourly.csv`，图5 读这张表；匹配口径（最近商圈、1000m 内才算命中）与长表一字未改。

一句话：**示例图里"长什么样"的部分我们跟了，"数出来多少"的部分我们保留自己的口径，
并把差异写清楚**——答辩被问到"为什么和示例不一样"时，答案是这里，不是临时解释。

### 清洗代码：老师的 9 条规则，8 条一模一样，1 条故意不照搬

老师那份 `clean_data()` 逐条对过，规则 1/2/3/5/6/7/8/9 与我方实现完全等价（只是我方拆成了
9 个可单测的函数，老师是内联在一个函数里）。唯一实质差异在**规则4 的时间戳判据**，我方不采纳：

- 老师写的是整列二选一：`if num.notna().all() and (num.abs() >= 10**12).all()` 走毫秒戳分支，
  否则整列按日期串解析。只要有一行时间戳是脏的，`.all()` 就为 False，**整列**改走另一条分支、
  全部时间变 NaT。
- 该判据只有下界没有上界：14 位日期串 `2018100304122` 同样 `>= 1e12`，会被当成毫秒 epoch
  解出 **2609 年**。
- 我方 `data_clean.py:63` 是逐行判断 + 上下界 `[1e12, 1e13)` + 不可解析行删除。
  实测本份数据 532,828 行 time 全部是 13 位毫秒戳（非数字 0 行、14 位日期串 0 行），
  老师那句 else 分支在这里是永远走不到的死代码；换成老师的写法等于把已经修掉的 bug 请回来。

照搬采纳的两处小改进：每条规则各包一层 `Timer`（实测全量 3.1 秒，规则4 独占 1.49 秒 ≈ 48%，
删行最多的是规则8 分钟去重 66,777 行），以及把原始四列列名收进 `config.RAW_COLUMNS`
（此前写死在 `read_raw()` 里，违反本项目"路径与阈值只在 config 出现一次"的约定）。
